# TerraWise Supabase security and persistence audit

Audited 12 November 2026. The project owner reports that email confirmation, login, field saving and separation in the UI have been tested with two real accounts. Those reports are not direct API or live-policy verification. No SQL, live user-data writes, deletions, or account sign-ins were performed during this audit.

## Findings

| Area | Evidence and result | Limit |
| --- | --- | --- |
| Authentication | `src/context/AuthContext.tsx` uses Supabase email/password methods, a persisted session, auth-state notifications, recovery, and sign-out. The app uses the public client key. | Real sign-up and login are owner-reported. The automated session and logout checks use synthetic responses. The UI session does not itself enforce database security. |
| Owner policies | `supabase/migrations/20261111_workspace.sql` enables RLS, revokes anonymous privileges, grants authenticated table access, and scopes SELECT, DELETE and UPDATE `USING`, plus INSERT and UPDATE `WITH CHECK`, to `auth.uid() = owner_id`. | Source review is not live policy verification. Other permissive policies, grants, roles or privileged clients can alter effective access. A table owner or service-role client bypasses normal RLS. |
| Anonymous access | The live read-only probe returned HTTP 401 and PostgreSQL 42501 with table privilege denied. | This tests one anonymous SELECT, not authenticated owner isolation or all permissions. |
| Data separation | Account workspaces load by account ID and do not read the guest fields, plans or analyses as their initial data. Browser-local soil report attachments are disabled for account workspaces. Isolated synthetic browser tests cover guest/account switching. | Existing guest data is not automatically uploaded or merged. Browser auth sessions remain stored by the Supabase client; local browser storage is not protection from XSS or another person with access to the browser profile. |
| Persistence and logout | Workspace changes are sent to Supabase; session persistence and sign-out are enabled. Isolated synthetic browser tests cover reload, sign-out, account switching and an outage. | Owner reports real field persistence. Live session expiration, refresh, sign-out across devices and cross-device synchronization were not independently verified here. |
| Concurrent writes | Client writes use owner and version predicates; duplicate initial rows and missing version matches raise a conflict. Synthetic browser tests simulate a newer remote version and verify that a stale write does not overwrite it. | This is optimistic concurrency for cooperating application clients, not a database-enforced version policy. Resolve a conflict by preserving/exporting unsaved data and reviewing the latest server version; there is no automatic merge. |
| Metadata refresh | Workspace loading now depends on owner and explicit retry, not changing account display metadata. A synthetic auth event confirms it does not reload over failed unsaved edits. | Closing the tab or an external sign-out can still discard unsynced in-memory changes; the export intentionally excludes some legacy/simulated content and report files. |
| Credentials and repository | `.env.local` is ignored and untracked. Pattern scans of the working tree, index and available history found no likely secret-key/private-key patterns; privileged-JWT pattern scans of source, static assets, scripts, build and available history found none. The Vite guard rejects known privileged key formats in `VITE_` variables. | Pattern scans are not proof that every secret or past leak has been found. Publishable keys are intended to be visible in browser bundles; never place a service-role or secret key in frontend configuration. |
| Reports | The browser report store is local-only; the private Storage policy file under `supabase/planned/` is a draft, not a deployed feature. | Cloud report upload, private-bucket policy verification and cross-account file isolation remain unimplemented. |

## Two-account authenticated API verification design

Do this only in a **separate disposable Supabase test project**, with fresh accounts A and B and synthetic fields. Do not run the write or delete probes against existing user workspaces: if RLS is misconfigured, a negative test could actually change or delete the target row. Keep passwords and access tokens out of chat, logs, screenshots, shell history and source files. Use separate authenticated Supabase clients and keep tokens in process memory; assert outcomes without logging request headers or response bodies containing personal data.

1. Confirm both clients are truly signed in as different users. Start with no workspace row for A. Let B create its own synthetic workspace through the application. Establish an anonymous client separately.
2. **Cross-owner INSERT:** Before A has a row, have B try an ordinary INSERT with `owner_id = A` and a synthetic payload. Expect an RLS/permission error, typically PostgreSQL 42501. A duplicate-key error is **not** proof of RLS protection. If the insert succeeds, stop: the disposable test project is unsafe.
3. Have A create its own synthetic workspace. Confirm that each account can SELECT its own workspace. Have B SELECT with `owner_id = A` and expect zero rows; test A selecting B as well. Also test that an unfiltered SELECT never includes the other owner's row.
4. **Cross-owner UPDATE:** Record A's synthetic row and version in test memory. Have B PATCH A's row, using `Prefer: return=representation` and a harmless synthetic change. Expect zero returned rows or a denial, then use A's client to confirm every value and the version are unchanged. Repeat in the opposite direction. RLS filtering can make a blocked UPDATE look like a successful response with zero affected rows.
5. **Cross-owner DELETE:** Only in the disposable project, have B DELETE A's synthetic row with `Prefer: return=representation`. Expect zero returned rows or a denial, then confirm with A's client that the row still exists unchanged. Repeat in the opposite direction. A 2xx response alone is not proof that a row was deleted or that RLS is safe.
6. Test that an anonymous request cannot read either row or perform writes. Test owner INSERT, SELECT and UPDATE separately so a blanket denial is not mistaken for correct isolation. Perform any owner DELETE test only with disposable records and explicit operator approval.
7. Test session persistence by reloading after sign-in; sign out and reload to ensure the account view does not return without reauthentication. Test a second browser or device, and a stale-version conflict between two sessions of the same account. Preserve the unsaved view/export before reloading after a conflict.
8. In the Dashboard, inspect RLS enabled status, the four policies, other policies, grants and role privileges. Policies can combine permissively; the migration file alone cannot prove the effective live configuration. Document results without recording passwords, tokens or field data.

## Remaining operational work

Run the above direct API tests and review the live policies before claiming verified isolation. Verify backup/restore, retention, operator access, production HTTPS and security headers, account recovery, rate limits, and physical-device/session behavior. Do not enable cloud soil-report storage until private bucket policies, consent, cleanup and two-account file isolation have been implemented and tested.
